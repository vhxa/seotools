# The audit model (findings, rules, comparison, history)

This is the one place that defines what a finding means. It spans `@seotools/core`, the worker, the web app and the database; the other `AGENTS.md` files point here instead of repeating it. Read it before changing findings, rules, comparison, crawl history, the pages table or the exports.

## Pages and issues

- Listed in a sitemap is a `<loc>` or a line of a text sitemap (link type `sitemap`, `AuditedUrl.sitemaps`). An alternate, image or video an entry names is requested but has its own link type (`hreflang`, `image`, `media`). A sitemap parsed since then records `data.sitemapSize.references` (even `0`); one without it stored every URL as `sitemap`, so `loadSite` puts a URL that a sitemap also declared as an alternate in `sitemapsAmbiguous`: neither listed nor absent (`presenceOf` is `unknown`, no sitemap finding). Analysing such a crawl again does not repair it; only a new crawl records the origin. Never infer it otherwise.
- Which issues exist, their order, group, type (`issue`, `warning`, `opportunity`) and importance live in `ISSUE_CATALOG` (`@seotools/core/crawl/issues`, pure so client components can import it); how each is detected lives in `CHECKS` (`apps/worker/src/crawl/issue-checks.ts`). Each issue needs `PageIssues.<id>.name` and `.description` in both message catalogs (a test fails otherwise) and a scenario in `issue-checks.test.ts` (likewise). An issue whose input does not exist yet (`indexed-not-in-sitemap` needs a source that confirms indexing) keeps its check and stays silent until it does.
- Issues belong to any URL of a crawl, not only pages: an issue filter ignores the view (`crawlUrlWhere`), which the pages table states by listing it as the `all` view. URLs the crawler only tried on its own (`isGuess`: other schemes and `www` of the home page, well-known files) are not blamed for failing.
- Checks read what the crawl stored, never the HTML: anything new a check needs goes in `CrawlPageFacts`, gathered by `PageFactsCollector`, and only shows from the next crawl. A fact added later is optional in `CrawlPageFacts` and not in `emptyPageFacts()`: `undefined` means a crawl from before it did not look, never that the page has none, and its check returns no finding (a test analyses facts without the field). The silence must not read as "absent" in a comparison: list the fact in `OPTIONAL_FACT_ISSUES` (`apps/worker/src/crawl/observed-inputs.ts`; TypeScript fails until every optional fact is listed, with the issues that read it). `analyseCrawl` stores the issues whose input is missing on any page as `unobserved` in the crawl's `auditSnapshot` (not configuration: `auditScopeKey` ignores it), and `observe` reads those issues in that crawl as unknown (`unobserved`), so they are never `new`, `resolved` or fixed against it. Its input is untrusted, so bound what it keeps and what it runs regexes on. The worker stores issues when a **full** crawl ends (`analyseCrawl` → `crawl_url_issues`); crawls from before a check existed show as not checked.
- Type is about the finding, importance about how much it matters, and they are independent: `issue` is for crawling and indexing problems, `warning` for what needs review (a serious security problem is a high-importance warning), `opportunity` for improvements. Lists of priorities order by importance, then type (`compareIssueSeverity`), so a type never buries something serious. There is no setting for what counts as "with issues": the overview counts the **audited** pages that have something of each type (`pagesWithType`, a page can be in several). Crawls store the `ISSUE_CATALOG_VERSION` they were analysed with and the worker analyses the others again at startup, so a catalog change reaches earlier crawls; bump `CHECKS_REVISION` when a check changes without the catalog changing.
- Indexability is a technical fact, never inferred from findings: `assessIndexability` (`@seotools/core/crawl/indexability`) says `indexable`, `not-indexable` (with its blockers) or `unknown` (not requested, request failed, not a page: never read as "expectation met"). A page is HTML that answered 2xx (`URL_VIEWS`): a page, script or image that fails is an error (the `errors` view), never a page, and "Indexable pages" count over every page, excluded or not. What a URL is follows how it answered, not what it was meant to be. Keep three things apart everywhere: what the crawl saw (indexability), what the user expects (`IndexIntent`), and whether a search engine indexed the URL (unknown). A robots.txt block is a blocker but never proof that a URL is out of the index.
- Rules and exceptions (`@seotools/core/crawl/audit`, table `audit_rules`, one row per statement, per domain and independent of crawls) make statements about the URLs a selector covers, each decided on its own with the same precedence: `audit` (participation: excluded URLs are crawled and keep their data but get no findings, and are not audited pages), six conditions (`noindex`, `nofollow`, `robots` for a robots.txt block, `sitemap` for being listed in one, `canonical` for declaring another canonical URL, `unlinked` for no internal anchor links), each `required` (a finding when it provably is not there), `allowed` (its generic finding is not raised either way) or `forbidden` (a finding when it provably is), and, as an advanced concept apart from the conditions, `intent` (what is expected of the URL's indexation as a whole: `indexable` by default, or `not-indexable`). A condition is about one observed state (directive, block, sitemap listing, canonical or inbound links): never read a `not-indexable` intent as a required `noindex`, a `noindex` as the URL's indexability, or a robots.txt block as the URL being out of the index. In the UI a rule is the rows that share a non-null `rule_set`, or a selector when it is null (`groupRules`; `planSaveRuleSet` saves them together); only path/prefix selectors may share a set, and URL exceptions always have a null set and one editor (`AuditStatements`) serves rules and URL exceptions; the form of a rule carries all its paths, so saving replaces the set. Selectors are exact URL, exact path or path prefix by segments, never regexes. A path or prefix is `literal` or `shared` between the language directories the domain declares (`domain_audit_config`; nothing is deduced from paths; at most one declared directory is taken off, only to resolve rules, never in URLs). Precedence: exact URL, literal exact path, shared exact path, the prefix that covers more of the URL (literal wins a tie), default; a rule for a query beats one that ignores it. An exception on one URL is a rule whose selector is that URL: tables, details and settings all edit the same rules, and "according to the rules" (`inherit`) in the UI means deleting that statement of the exception, which is not "no change" (a statement left out of the request, which `planUrlConfig` never touches: a multi-URL change sends only what the user chose). Each statement inherits on its own: an exception for one condition never states, resets or copies another. Resolution lives only in `compileAuditRules`: do not re-implement it. Exclusion and conditions are applied once, in `applyAuditPolicy` (`issue-checks.ts`), after every check ran, so the other URLs keep judging an excluded one as it really is; only the comparison sets for duplicates leave it out. Never put an exclusion inside a check. A condition a rule states replaces only its own generic findings (`GENERIC_OF`): never a conflict of directives or a `rel="nofollow"` link. What other pages say of the URL (an inbound canonical or hreflang) is decided by the origin × destination policy below, not here. Disabled exceptions do not act: pages never show them as what a URL has.
- The default expectation (`indexable`) raises no finding of its own: the generic findings (`noindex`, canonical, robots) already say so. Only an expectation a rule states is judged (`expected-*` issues), only on pages that answered and were not merely tried by the crawler (`judgeable`), never on resources, redirects, failures or unknown data. `nofollow` never counts as `noindex`. A condition no rule states behaves as it always did (generic findings, with the expectation dropping `noindex` and `indexable-not-in-sitemap` for a `not-indexable` URL; a canonical elsewhere is a state of indexability, not a finding); one a rule states decides its own findings instead. Conditions are judged only on `judgeable` pages and only when the crawl could tell (`presenceOf`, `conditions.ts`): presence is proven by what was read, absence only by whole input (a page parsed whole, a robots.txt that answered or is a 4xx, every sitemap read in a `completed` crawl: `Site.sitemapCoverage`); anything else is `unknown`, which is never met nor missed and raises no finding. Sitemap and unlinked conditions are `site`-scoped: a recheck neither judges nor observes them. A positive internal anchor count proves linked; zero proves unlinked only in a completed crawl, never one cut at its URL limit. Canonical conditions are `url`-scoped: canonicalised proves presence and a whole parsed page proves absence.
- Findings come in three families, kept apart everywhere (not shown as such in the UI): indexation (`noindex`, robots.txt, canonical elsewhere, sitemap listing: the only ones audit rules decide), broken references (a canonical, hreflang, sitemap entry or link to a URL that fails or redirects: `*-broken`, `*-redirect`, `hreflang-unreachable`, `links-to-*`; never excused by any rule) and quality (content, accessibility, security, HTML: judged on every page whatever its indexation). The search-result ones among the quality findings (`SEO_CONTENT_ISSUES`) are secondary on a page the crawl saw as not indexable (`isSecondaryFinding`): listed, never counted as pending or in pages with findings. A finding about what a page links to or loads (`links-to-*`, `resources-broken`, `og-image-broken`) sits on the page that has the reference.
- Origin × destination (`apps/worker/src/crawl/relations.ts`, the one place): when a URL points at another (canonical, hreflang) the finding sits on the origin and is about the destination. Accept the canonical blocker exactly like noindex: a required or allowed canonical accepts it, forbidden refuses it, and with no canonical rule a not-indexable intent accepts it; name the canonical rule, falling back to the intent rule, as the accepting rule. An explicit indexable expectation still reports a canonical blocker even when another rule requires it. Since semantics 5 (`ORIGIN_RELATIONS_SEMANTICS`) only the origin's declarations excuse: an intentionally non-indexable origin (`isExpectedOut`: every observed blocker is accepted by its rules, never proof of search-engine index status) excuses the indexing blockers of what it points at and the missing return; a URL expected out has no `only-*-inlinks`; a destination declared out never excuses an origin expected to be indexable (semantics 4 let each blocker of the destination be accepted by its own rules: keep reading 4 that way). Never excused: redirecting or failing destinations, the declaration-internal hreflang issues, `sitemap-not-indexable`. App policy, not SEO fact; nothing is excused under a configuration older than `RELATIONS_SEMANTICS`; an excluded destination is accepted only by what is declared of it, and its technical state never changes. Route a new relation finding through `excusedBlockers`, never skip it inside a check.
- Figures that are conventions, not facts (title/description length, thin words, URL length, click depth, image weight) are per-domain thresholds (`AUDIT_THRESHOLDS`, `@seotools/core/crawl/thresholds`; `domain_audit_config.thresholds`, `db.audit.setThresholds`): checks read them only through the configuration being applied (`figures(site)` in `issue-checks.ts`), the snapshot keeps the ones that differ from the defaults and `auditScopeKey` includes them. Only what the analysis reads can be one: what the crawler measures while parsing is fixed. What is objective (a 404, a noindex) is never configurable.
- Every change to the rules, the language directories or the thresholds bumps `domain_audit_config.version` and queues one `audit.recompute` job in the same transaction. `analyseCrawl` takes the configuration to use, whole, and `saveAnalysis` refuses an analysis made with an older version than the crawl already has. Each crawl keeps the version, the rules, the languages and the meaning (`AUDIT_SEMANTICS`) it was analysed with (`auditSnapshot`): the catalog reanalysis uses those, never the current ones; only the latest full crawl follows the current ones. A snapshot without `semantics` is semantics 1 (default intent `none`, `none` rules, literal paths): never read it with today's defaults. Semantics 2 accepted the page's own `nofollow` through the intent rule (`acceptNofollow`, `inherit`); `compileAuditRules` and `readUrlAuditState` read that as the `nofollow` condition being `allowed`, and semantics 3 ignores both. Semantics 4 is the first that lets what a URL declares reach the findings of the URLs that point at it (`relations.ts`); an analysis of semantics 3 or older accepts none of it, so repeating it gives what it gave; semantics 5 takes that back from the destination and leaves it to the origin. Changing what a configuration means needs a new `AUDIT_SEMANTICS` and an idempotent upgrade of existing rules (`upgradeSemantics` with `planUpgradeSemantics(rows, context, from)`, run by `migrate()`: it deletes the `none` rules, which can bring back a broader rule they were holding off, writes accepted `nofollow` as condition rules without turning any expectation into a `noindex`, and, from 3 or 4, writes nothing but moves the version of a domain whose enabled rules `reachesRelations`, so its latest crawl is analysed again). `auditScopeKey` ignores rule grouping (`set` / `rule_set`): regrouping unchanged statements does not change configuration scope. `auditScopeKey` reads 3 as 4, and 4 as 5, only for a configuration without such a rule. Pages must say when results are behind the configuration (`auditResultsState`), never show them as current.
- A finding a rule takes as expected is **accepted**, never fixed: it goes in `crawl_url_accepted_issues` (`detectFindings`), not in `crawl_url_issues`, so nothing pending counts it, with what accepts it (`FindingAcceptance`, `@seotools/core/crawl/acceptance`) and the URL whose declaration does (`acceptedBy`), which tells when a rule of one URL acts on others. Whatever `applyAuditPolicy` or `relations.ts` keeps from being reported is recorded there, except an excluded URL (which has no findings) and what `expected-indexable-blocked` reports in other words. Keep four things apart everywhere: fixed (the crawl no longer sees it), accepted (it does, and a rule expects it), dismissed (a person decided not to act), unknown (it could not tell).
- A dismissal is a person's decision, never a rule: store it in `finding_states`, record it as a `dismissal` acceptance and keep the acting decisions in the analysis snapshot's `dismissals`. Apply it after rules and relation acceptances, never inside a check. Keep the decision maker and time in the snapshot and acceptance; historical views never take attribution from a mutable current row, and show its note only while id, dismissed state and time still match. A dismissed finding is never fixed; `expected-*` findings cannot be dismissed. A URL decision overrides the domain decision; `in-progress` is only a label and changes no counts.
- History and comparison read what retained full crawls stored and never request anything. `?crawl=<id>` on `/urls` and `/urls/[hash]` browses any `completed`/`incomplete` full crawl (the latest without it): resolve it only with `selectCrawl`/`findCrawl` (`lib/crawl-history.ts`), which ask the database with the domain, so another domain's crawl is a 404; a pruned crawl keeps, for its domain's `historyDays`, the compact history of what each URL was (`crawl_url_history`, `history`; `keepsUrlHistory`), then only its totals, and is never shown as empty. Retention keeps the full results (links, evidence, data) of the newest `retainCrawls` usable crawls (2 by default: what a comparison needs); bootstrap applies it to every non-archived domain and compacts SQLite (`db.compact()`). A comparison (`/crawls/compare`: `compareCounts`/`compareUrls`/`countCompared`) and a URL's history (`urlHistory`) page on the server and refuse crawls that are not full, retained crawls of the domain. Per-issue change counts for web summaries and worker alerts go through `compareWithPrevious` (`packages/db/src/changes.ts`), which reads URLs in bounded batches; use exact mode for web counts. What a change is called lives only in `@seotools/core/crawl/compare`: a URL missing from the later crawl is "not seen", never "deleted"; a finding is `new`/`resolved`/`reappeared` only when every crawl involved could have reported it under the same issue catalog, the same expectation and conditions for the URL and, for an issue that looks at other URLs (anything not in `PAGE_LOCAL_ISSUES`), the same audit configuration and a crawl that was not cut at its URL limit; `reappeared` needs the crawl in between (or before) that shows the absence. Otherwise it is `unverified` (with reasons), `excluded` (removed by policy) or `audited`. Add an issue to `PAGE_LOCAL_ISSUES` only if it depends solely on the URL's own answer. Older crawls keep their snapshot: pages show their date, coverage and audit configuration, never recalculate them.
- The pages table (`/urls`) filters, sorts and pages on the server: its state is the address (`lib/pages-query.ts`), never client state, except row selection and table preferences (visible columns and widths, in `localStorage`). Share view and filter definitions through `@seotools/core/crawl/listing`; preserve `other` for old links and worker site loading. Mark inapplicable filters as not applied and omit them from queries (`unappliedFilters`, `listingOf`); changing views clears the issue and incompatible filters while retaining search and order (`detailHref`). Distinguish filtered counts from view totals. The URL detail drawer opens client-side with a skeleton while the server renders `?url=<hash>`.
- The Structure page (`lib/structure.ts`) counts per directory with the same definitions as the overview: pages are HTML that answered 2xx, errors are the `errors` view, and a page has a finding of a type by the `pagesWithType` rule (audited, secondary findings left out). Keep `countsOf` in step with `analyseCrawl`; it never shows findings for a crawl whose analysis is not current. Its links narrow `/urls` with the existing search (`host/path/`): there is no path filter.
- CSV exports (`/domains/[host]/urls/export/[kind]`: `pages`, `findings`) list exactly what the table's address lists: the same `parseDetailQuery`, `unappliedFilters`, `listingOf` and `selectCrawl`, behind `requireDomain`, with no second reading of the query. They stream, a bounded batch of URLs at a time, in the table's order (`crawlUrlOrder` is total: the hash breaks ties, so paging never skips or repeats), and stop when the client goes away. A missing, pruned or never-analysed crawl is an error, never an empty file. Cells go through `csvCell` (`lib/csv.ts`), which neutralises spreadsheet formulas in everything a site wrote; a value the crawl did not store is an empty cell. Each column is an entry of `PAGES_COLUMNS`/`FINDINGS_COLUMNS` with its header in `Export.columns`.
- Paginate URL links from stored crawl data and resolve requests within the domain (`findCrawl`); pruned results must not appear empty. Group link kinds through `@seotools/core/crawl/links`. Links live in `crawl_url_links`, by the crawl's `ref` and each URL's `seq` (coalesced variants keep one row per source, target and kind, with the first link context; the crawler numbers URLs as it finds them; `foundFrom`/`foundKind` say how it got to each): never store hashes or ids per link row, it is the largest table. Where a link sits (`LinkContext`: text, element, landmark, and the opening tag where it brings in query parameters) is what the page said, bounded; never invent anchor text or attributes that were not stored, and treat outgoing links from unread URLs as unknown. A URL asked for as a script, stylesheet or image is a resource whatever it answers (`RESOURCE_REFERENCES` in the engine).
- Findings of the issues in `ISSUE_EVIDENCE` (`@seotools/core/crawl/evidence`) carry bounded evidence: which images, links, canonical declarations or other pages make the URL have it. It is gathered while parsing (`PageFactsCollector` keeps the total in the counters of `CrawlPageFacts` and only the first `MAX_EVIDENCE_ITEMS` samples, with text cut) or during analysis from stored page values or the comparison sets of `loadSite` (which never hold excluded URLs), and stored inside `crawl_url_issues.details` (`serializeIssueDetails`: rows without evidence keep the old array). A finding of such an issue without evidence means the crawl predates it: the UI says so and never invents examples. Show evidence addresses only through `evidenceTarget`, never as raw `href`s or HTML.

- Strip ignored query parameters only for internal crawl identity, before hashing, queueing and link destination lookup; preserve written declarations for audit checks and link context, and compare each crawl’s stored ignored-parameter snapshot (legacy: `[]`).
