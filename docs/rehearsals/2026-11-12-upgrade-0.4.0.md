### Native diagnostics and limits

A temporary diagnostic image added only `gdb` and `strace` tooling to the target image;
repository/product code was not patched. One worker-only bind run and three bind runs with
web started separately under a shell and the worker under GDB completed all three reanalyses
without SIGBUS. They were observed for over 40 seconds before deliberate shutdown. Thus no
SIGBUS native backtrace was captured; debugger timing changes the startup schedule and these
passes do not exonerate any particular SQLite call.

The explicitly requested privileged `nsenter -t 1 -m -u -n -i dmesg` probe was attempted using
tools already available in the application base image, instead of pulling Alpine. Docker
rejected namespace access: `nsenter: reassociate to namespaces failed: Operation not permitted`.
No VM kernel fault trace was available. `--report-on-signal` was not treated as a SIGBUS handler.

The database connector enables WAL in `packages/db/src/dialects/sqlite.ts`. The **measured
`PRAGMA mmap_size` is already 0**. That setting controls database-file mapped I/O; it does not
eliminate the separate WAL shared-memory index. SQLite documents that clients mmap the `-shm`
file for WAL coordination ([WAL file format](https://www.sqlite.org/walformat.html),
[mapped database I/O](https://www.sqlite.org/mmap.html)). Docker recommends VM-local named volumes
for databases on Desktop ([settings/file sharing](https://docs.docker.com/desktop/settings-and-maintenance/settings/)).

### Diagnosis and proposed fix

**Best-supported diagnosis:** an intermittent native SQLite/WAL failure associated with the
macOS shared bind-mount path and startup/reanalysis workload. It reproduced in both application
versions, and did not reproduce in three target upgrades using VM-local named volumes. A
shared-memory mapping/coherence fault is consistent with SIGBUS and the filesystem dependence,
but **the exact faulting instruction, mapped file and triggering SQL call remain unproven**.
Do not present this as a proven VirtioFS-specific bug, SQLite corruption, or a new jobs-prune defect.

The relevant shared application path is `worker.main` → `reanalyseOutdatedCrawls` → `analyseCrawl`
with a WAL database also used by the web process. This locates the workload that exposes the
failure, not the precise native instruction. The published old image's equivalent path also
fails. `db.compact()` is called only by bootstrap; `docker/entrypoint.mjs` waits for bootstrap
and its database close before spawning web/worker. These trials therefore provide no evidence
of bootstrap VACUUM racing a still-running web process of the same container. No other app
container was running against a tested database.

**Smallest demonstrated remedy:** use a named Docker volume for SQLite `/data` on macOS Docker
Desktop and document that recommendation, with backup/restore into the volume. No product-code
patch is justified by the current evidence. In particular, adding `PRAGMA mmap_size=0` would be
a no-op here and would not disable WAL shared memory. A code change to stagger web/worker DB
opening, change journaling, or alter native SQLite settings needs a controlled reproduction and
validation first; GDB's changed scheduling alone does not prove serialization fixes it.

**Linux installs:** native Linux named volumes and bind mounts on local ext4 do not traverse
macOS host sharing; the VM-local ext4 results are encouraging for those deployments. A separate
Linux host was not tested, so absence of risk there is an inference, not a guarantee. Docker
Desktop shared mounts on other hosts and network filesystems are not covered by the ext4 passes.
No 0.4.0 release approval, PostgreSQL validation, downgrade probe or authenticated UI validation
is implied by this diagnosis.
