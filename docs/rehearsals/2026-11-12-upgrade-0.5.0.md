## SQLite downgrade refusal

Published 0.4.0 exited **1** in **0.176 s** on the upgraded volume, before web/worker startup:

```text
The database is newer than this image or has an unknown migration history. Refusing to start. Going back requires restoring the backup taken before updating, together with the previous image.
```

All table counts, migration pairs, eligible catalog groups, rule fingerprint and stopped
database file SHA-256 were identical before and after refusal:

`80a252ab6a3dd440b2ca4b35c634db3d7c49cabb2771d6cca1d01c2813e42885`.

Inspection checkpointed/closed the database before hashing. This demonstrates refusal, not
a backup restore or a working rollback. The harness initially missed the refusal message
because it captured only stdout; Docker logs confirmed the expected message on stderr.
That capture assertion was a harness issue, not a missing downgrade guard.

## PostgreSQL 17: transfer failed before upgrade

A PostgreSQL 17 container, named volume and internal network were created. The old image's
online SQLite backup was copied into another **writable named volume** for the supported
0.4.0 `migrate-db.mjs --from file:/data/baseline.db --to postgres://…` transfer.

The transfer ran before PostgreSQL was ready to accept connections and exited **1**:

```text
connect ECONNREFUSED <isolated-container-IP>:5432
The copy failed. Drop the PostgreSQL database, create it again empty and retry; the SQLite database was not changed.
```

**The rehearsal stopped here**, as required by the brief. No retry, product repair or
PostgreSQL upgrade/downgrade probe followed. This connection failure is a harness readiness
error and gives no evidence of a product migration defect. A future authorized run should
wait for `pg_isready` before attempting transfer into a fresh empty database.

PostgreSQL baseline counts, migration hashes, health, reanalysis, target upgrade and downgrade
refusal are **unverified**. No PostgreSQL contract database or tests were started.
