# Upgrade rehearsal: 0.5.0 to the 0.6.0 integration branch, and rendering with Compose as shipped

**Result: in progress.** This record grows step by step; the summary is written last.

Run date: **2026-11-14 UTC**. Source: `ee7727fc382012888839cb031b34abc9dc141014` from
`origin/feat/0.6.0`. Docker Desktop on macOS, **Linux arm64** containers for the whole run.
No product code was changed.

## Images and isolation

- Published baseline: `ghcr.io/vhxa/seotools:0.5.0`, pulled digest
  `sha256:16904ddd167aa1f6a26b003c4e373923d1512e2973edad020c97f41fa8c5c55c` (arm64).
- Local target: `seotools-rehearsal-wp7-target`, built with `docker build .` from a `git archive`
  of the exact commit, `SEOTOOLS_BUILD_COMMIT` set, default development channel; image ID
  `sha256:ae826c0813634d48377b406316819a06d317354e46c28efb157b20f6187f84f7` (arm64,
  537,326,771 bytes uncompressed).
- Browser: `chromedp/headless-shell:158.0.8127.18`, the tag pinned in `docker-compose.yml`, digest
  `sha256:830fa77e0602cb42e5cb2cbd9237ba27b649ad69d5fb82b54713aac8b7ab4f29` (arm64).
- The authorized historical backup was copied **once with `cp`** into a private temporary
  directory. A throwaway helper mounted it read-only at `/backup` and copied it into a named
  `/data` volume owned by UID/GID 1000. The owner's live database was never opened, read or copied.
- Every app container of the upgrade part had `SEOTOOLS_PAUSE_AUTOMATION=true`. Both images used
  the same random staging auth secret; no Google key, mail, bot test or request to the internet.
- SQLite app and helper containers used `--network none`; health was fetched at container
  loopback. All `/data` mounts were named volumes. Every container, network, volume, Compose
  project and local image alias created has the `seotools-rehearsal-` prefix. Host port 3000 and
  existing containers were untouched.
- Inspection ran a read-only script inside the app images (their own `better-sqlite3`/`pg` and
  migration files). Before each file hash, the stopped database was checkpointed and closed.

## SQLite downgrade refusal

Published 0.5.0 exited **1** on the upgraded volume, **0.196 s** after its container started
(0.399 s including the launch command), right after `database selected` and before web or worker
startup:

```text
The database is newer than this image or has an unknown migration history. Refusing to start. Going back requires restoring the backup taken before updating, together with the previous image.
```

Table counts, the 36 journal pairs, every finding row, the compact history and the rule fingerprint
were identical before and after, and so was the stopped file's SHA-256:

`30edf6f7012f8fb9faec23f134d8a952f2b2013e5a123e67a67cb878aa43543b`.

This demonstrates refusal, not a backup restore or a working rollback.
