# Upgrade rehearsal: 0.5.0 to the 0.6.0 integration branch, and rendering with Compose as shipped

**Result: in progress.** This record grows step by step; the summary is written last.

Run date: **2026-11-14 UTC**. Source: `ee7727fc382012888839cb031b34abc9dc141014` from
`origin/feat/0.6.0`. Docker Desktop on macOS, **Linux arm64** containers for the whole run.
No product code was changed.

## Images and isolation

- Published baseline: `ghcr.io/vhxa/seotools:0.5.0`, pulled digest
  `sha256:16904ddd167aa1f6a26b003c4e373923d1512e2973edad020c97f41fa8c5c55c` (arm64).
- Local target: `seotools-rehearsal-wp7-target`, built with `docker build .` from a `git archive`
  of the exact commit, `SEOTOOLS_BUILD_COMMIT` set, default development channel; image ID
  `sha256:ae826c0813634d48377b406316819a06d317354e46c28efb157b20f6187f84f7` (arm64,
  537,326,771 bytes uncompressed).
- Browser: `chromedp/headless-shell:158.0.8127.18`, the tag pinned in `docker-compose.yml`, digest
  `sha256:830fa77e0602cb42e5cb2cbd9237ba27b649ad69d5fb82b54713aac8b7ab4f29` (arm64).
- The authorized historical backup was copied **once with `cp`** into a private temporary
  directory. A throwaway helper mounted it read-only at `/backup` and copied it into a named
  `/data` volume owned by UID/GID 1000. The owner's live database was never opened, read or copied.
- Every app container of the upgrade part had `SEOTOOLS_PAUSE_AUTOMATION=true`. Both images used
  the same random staging auth secret; no Google key, mail, bot test or request to the internet.
- SQLite app and helper containers used `--network none`; health was fetched at container
  loopback. All `/data` mounts were named volumes. Every container, network, volume, Compose
  project and local image alias created has the `seotools-rehearsal-` prefix. Host port 3000 and
  existing containers were untouched.
- Inspection ran a read-only script inside the app images (their own `better-sqlite3`/`pg` and
  migration files). Before each file hash, the stopped database was checkpointed and closed.

## Rendering with the Compose file as shipped

`docker-compose.yml` was copied unchanged (same SHA-256 as the repository file,
`bf9a01c0436c0a0751a02f20deda5bba99c81c9d74d70b16dac82e86c5e80fb5`) into a private directory and
run with the target image under the Compose project `seotools-rehearsal-wp7-compose`. Exactly what
was added:

- **`.env`:** the staging `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL=http://localhost:3330`,
  `PORT=3330` (the published port), `SEOTOOLS_IMAGE=seotools-rehearsal-wp7-target`,
  `SEOTOOLS_PAUSE_AUTOMATION=true` and `CRAWLER_ALLOW_PRIVATE_NETWORKS=true` (the fake site has a
  private Docker address). For step b, the three lines of `docs/rendering.md`:
  `COMPOSE_PROFILES=rendering`, `RENDER_BROWSER_URL=http://browser:9222`, `RENDER_CONCURRENCY=2`.
- **An override file** adding one service, `fakesite`: `node:24-trixie-slim` running a 30-line
  static server (read-only bind mounts of the server script and the site, never `/data`) on the
  app's `default` network, with the aliases `shop.rehearsal.test` and `www.shop.rehearsal.test` so
  every seed the crawler requests resolves inside Docker. `www.` answers 301 to the apex; HTTPS
  seeds are refused (nothing listens on 443). It logs every request (time, method, host, path,
  User-Agent and, from step c on, client address).
- For the negative cases of step c only, two more override files that replace the browser's
  `command` with nothing (no isolation flags), one of them also adding the `default` network.

**The fake site** (19 files under a private `/tmp` directory), all internal links relative:

### d. The browser killed mid-crawl

The browser was restored exactly as shipped (`docker compose --profile rendering up -d browser`
with only the fake-site override) and **Check now** stored `ready` again. `docs/rendering.md` gives
the window: an unavailable browser pauses the crawl for up to ten minutes in total, polling every
30 seconds, and never falls back to HTML. `caffeinate -i` kept this Mac awake for both runs.

**(i) Killed and back within the window.** A rendered crawl was started; when 4 of its 13 pages had
been rendered (20 of 31 URLs done), the browser's main `headless-shell` process was killed with
`SIGKILL` from inside the container, like a crash. The container exited and Compose's
`restart: unless-stopped` policy restarted it **0.56 s** later. The crawl paused, spent
**32.7 s** of its allowance (one 30-second poll plus the check), checked the new browser instance
(stored `ready` at 20:31:04), resumed and **completed**: 13 pages, 31 URLs, 13 renders (2 unsettled,
as in step b), 64.6 s. Its findings with details have the **same SHA-256 as the three crawls of step
b** (`32cf77d732f324b571a65b5bd84523dce4f2749baf71b83f824c76aa07abc6a0`); the crawled URLs and the
status, settled flag, final URL and failure of every render row are identical too (the render rows
equal crawl 2's, including its `requests.cached` counter).

**(ii) Killed and left down.** Another rendered crawl; at 4 of 13 renders (20 of 31 URLs) the browser
was stopped with `docker kill` (exit 137), which the restart policy does not undo. The crawl paused
with 6 pages and 23 URLs done and stayed exactly there. The fake site received **no request** after
the kill, so nothing continued on HTML. The crawl ended **`failed` with `browser-unavailable`**
**600.4 s after the kill**, with `browser_wait_ms` = 600,000: the documented ten-minute allowance,
measured awake. It has no analysis, no findings, no accepted rows and no snapshot. The crawl list
shows it as "failed · Rendered · Not analysed", and the previous completed crawl stays the latest.
